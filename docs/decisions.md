# Wmap decisions

A register of decisions that are implemented, with the reason and the evidence, kept apart from proposals. [architecture.md](architecture.md) is the original design plan, written before the first build; where they differ, this register and the code are current. Change history: [CHANGELOG](../CHANGELOG.md). Verification: [testing.md](testing.md).

Status: **implemented** (in the release named), **proposal** (not built), **superseded**.

## Implemented

| WM-D01 | A standalone atlas with its own renderer and viewport. Fast Map is neither required nor reused | One continuous camera across the cylinder seam and a 100× zoom range need control of the projection, the tile pyramid and the shader | 0.1.0 |
| WM-D02 | The server bakes one **semantic world chart** (coast distance, height relative to sea, ice, river distance) and clients evaluate the style per pixel in a shader | Zooming and style switches cost no new data; the seam is continuous by texture repetition; ink keeps its screen width. Colour tiles would need re-rendering per style and zoom | 0.3.0 |
| WM-D03 | Predictions never generate chunks. Detail finer than the chart is sampled on demand from the provider and cached on server and client | Chunk generation at world scale is unaffordable; a bake must not change the world | 0.1.0 |
| WM-D04 | Other mods are integrated by reflection, validated once at world start, with no compile-time dependency. Cross-mod contracts are attributes (`wmapWindInstrument`, `wmapWindSight`) | Each mod must load alone. A missing or changed integration disables that feature with a log line instead of a crash | 0.1.0 |

A recorded tile keeps its own water instead of the chart's predicted river courses | A prediction is a model of the generator; the recorded terrain is what was generated, with structures and edits. The architecture plan required this; 0.3.7 drew recordings only when predictions were not shared, so a wrong coast stayed wrong after a visit | 0.3.8 |
| WM-D12 | A **flat prediction** (land/sea mask with invented heights: Cylinder World without Earth Map) is flagged in the manifest (`AtlasInfo.FlatPrediction`). One-block detail of an ocean-map mask is wasted sampling | 0.3.8 |
| WM-D13 | `PredictTerrain: false` charts recorded terrain only, keeping topology and geography | The escape hatch for generators Wmap cannot predict. Exploration and recordings are keyed by topology, so they survive switching | 0.3.8 |
| WM-D14 | The prediction cache key contains only what shapes terrain: savegame, seed, mod versions, provider assembly revisions, Earth's parameters, Cylinder's saved protobuf layout (without mist and jump-fog settings), Cylinder's `FlattenSeabed`, and Terra Prety's settings when it is loaded | 0.3.7 serialised the whole live Cylinder parameter object, including the sea-ice date, so a restart on another day re-baked the world. External generator settings were missing | 0.3.8 |
| WM-D15 | The server paces world chart transfers: a player's chunk requests are deduplicated and capped at 32 pending, and Tick sends at most 8 chunks per player and 16 in all per 50 ms tick (10 and 20 MiB/s), starting with a different player each tick. Requests are queued without main-thread work | With a shared chart any client could request the same 64 KiB again and again. The cap is above the client's 16-chunk window, so an honest download loses nothing; the rotation keeps two busy downloads from starving a third | 0.3.8 |
| WM-D19 | Hello and tile-request packets reach the main thread only while the player has fewer than 32 such callbacks waiting; the rest are dropped on arrival | Each packet queued a main-thread callback before any validation, so a flood of even invalid requests grew the queue without bound. Honest clients keep 8 tile requests in flight and send a hello every 3 s | 0.3.8 |
| WM-D16 | A recorded water sample stores its **bed** as the height and the water above it as the depth, like a prediction. The bed comes from worldgen's terrain height, or a scan down through the liquid where that is missing. Old recordings are not migrated; a cell is rewritten when its place is seen again | 0.3.7 stored the water surface as the height, so recorded seas had no depth. Invalidating recordings would also have cleared every player's exploration, which shares their folder | 0.3.8 |
| WM-D17 | A map that does not wrap does not wrap texture coordinates, and the shader draws nothing beyond its east and west edges | The camera clamps to the east edge, where wrapping put the west edge's data | 0.3.8 |
| WM-D20 | Cylinder's seam band is predicted by calling `SeamParams.SeamGround(x, z, natural)` on every column within `SeamWorkReach` that the polar worldgen does not own (Cylinder 0.11.5 and later), and its exact polar-zone seabed by `SeamFloorY`. A column whose ground `SeamGround` leaves unchanged keeps the provider's sample. Older Cylinder builds use Wmap's copy of the v9 formula | Cylinder 0.11.5's layout v10 band has relief, a wavy edge and a ramp past the half-width that a copied formula would have to follow version by version. Cylinder's worldgen calls the same pure function and leaves such a column untouched. The cache key already includes Cylinder's assembly revision and saved layout version | 0.3.9 |
| WM-D18 | A failed write keeps recordings and the exploration mask unsaved; they are written again (recordings after 10 s) and on exit. Exploration writes to one file run in order, across sessions. A new session waits up to 2 s for the last write; if it is still running, or the saved mask cannot be read at start, the session merges the file into its mask once it can be read, and into each of its own writes until then (exploration only grows, so merging is a maximum). A write whose merge cannot read the file fails and is retried. A recording that cannot be read (locked, a disk error) stays unloaded and unedited, and is read again after 5 s; a damaged one, truncated included, starts empty | 0.3.7 marked them saved when the write was queued, so a transient disk error lost them; a slow final save could be overtaken by an older one; an unreadable recording was loaded as empty and then saved over the file | 0.3.8 |
| WM-D21 | Far terrain starts at 0.75 × the game's view distance, where the game's water begins to fade, not at the view distance. | WM-D23 | The near band and climate tiles live in 8 × 8-slot toroidal texture atlases addressed by unwrapped tile ids counted from the far-terrain origin's lap (`FarTileWindow`, mirrored in `wmapfartiles.ash`). | WM-D24 | Stitched vertices average the **final** displaced height (chart/band blend, canopy, push-down) at their coarse edge's ends | Averaging only the chart, then adding position-dependent terms, cracks ring edges wherever the band weight, forest or push-down changes | 0.4.0 |
| WM-D25 | Missing detail fades out: per tile over 1.5 s after it arrives, and in space through one readiness field: every tile within 48 blocks of a point (diagonals, the tile beyond a short seam tile, its own at distance 0) scales it by `mix(smoothstep(0, 48, distance), 1, readiness)`. | WM-D26 | Far colours use the game's own climate tint maps (`planttint`, `watertint`) with vanilla's altitude adjustment, from Earth's stored climate-map pixel; forest canopy (8 blocks) from Earth's `ForestPotential`, on land only (coast distance), never on lakes or ice. | WM-D27 | (Superseded by WM-D29 before release.) The client **records every block** of the chunks around the player (the one-block level); coarser levels keep one sample per cell, from its centre. **Recordings draw over every prediction**, finer or not, and at close zoom the four-block recordings are drawn too, under the one-block ones | WM-D11 let one-block predictions draw over four-block recordings at close zoom, so story locations and edits vanished when zooming in (reported in game, 0.4.2). | WM-D28 | **Charting by line of sight** is a CPU viewshed over the world chart's heights (half resolution, each cell its highest point; water at its surface): rays one cell apart at the far end, each keeping its steepest angle, from the eye all around, out to `SightDistance`, plus a `SightCircle`. | WM-D29 | The recorder takes **four-block samples** of every chunk and records a 4 × 4-block cell **block by block only where the world differs from the prediction** (far terrain's near band: land against water, or more than 3 blocks plus 3 % of the height) or where the game reports a block changed; without a prediction, where the top differs from the generated terrain by more than plants or water. | WM-D56 | **Far terrain is drawn in three passes, and covers the game's fading blocks at any distance** (amends WM-D55). Before the game's chunks (render order 0.36 < 0.37): (1) depth only, (2) colour where (1) left the surface nearest (depth test LEQUAL, no depth writes), the distant lights against it, (3) the cover: where far land lies past 0.8 of the view distance and below the clouds' underside (the game's cloud level less 16 blocks, above the camera), the depth of the point at 0.8 along the ray. ## WM-D40: play-test #19 and #22 surface recording (0.5.0-pre.12, 30 October 2026)

**Decision:** a fine recording is evidence of a prediction difference, not evidence of a building. Only a dry recorded top more than three blocks above `WorldGenTerrainHeightMap` may produce a structure box. Store that evidence in WCL6's colour metadata; keep WCL5 colours and lights, without inventing structure evidence. Preserve terrain, exploration and paper-map precedence. Reject incomplete/air canopy scans and retry them; snow over foliage must go through the foliage scan. Predict Earth's later RGI/frozen-freshwater surface passes through the optional Earth adapter until Earth supplies a final-surface query. **Recorded terrain/water is authoritative:** all predictions draw before all observations, fine observations over coarse observations; cached observed fallbacks obey the same order, observations remain opaque through zoom fades, and recorded overview levels correct the world chart too. Unknown observation cells retain zero coverage. This supersedes WM-D29's permission for finer predictions to cover coarser observations.

### Causes and production calls

* **#19 (Wmap):** `ObservedTerrain.Tick` flags natural coasts and height mismatches for fine recording. `RecordedTiles.Derive` previously boxed **every** dry fine cell. `farcells.vsh::structure` then stretched its top colour down to the smoothed predicted ground. A cliff sampled above that smooth mesh thus became a column, including a pale sand/snow top stretched down its sides. In addition, `Classify` checked growth before stripping snow: a snow-covered canopy became white land at treetop height. Its 48-block scan could also end in unloaded air and store that as land. These paths reproduce the reported disappearing-at-real-chunks behaviour; the original client recordings are unavailable, so the exact top block responsible in the Fuji screenshots is not established. No evidence of erroneous tall columns from Earth's height sampler was found.
* **#22a (Earth API omission, compensated in Wmap):** `WorldSource.Create` snapshots the live model and `EarthSampler` compiles a call to **`TerrainModel.GetColumn(double,double)`**, reading `Top`, `WaterTop`, `Water`, `IceBottom` and `River`. `ColumnSample` already maps `IceBottom <= Top` to ice, and both semantic encoders and both map styles already support it. However, Earth pre.8's `EarthWorldGen.Surface` applies RGI ice **after** the column terrain, from saved `Params.Glaciers`, `Data.HasGlaciers`, `TerrainGeoAt` and `GlacierCoverage >= 0.5`. * **#22b (Wmap presentation of that omission):** the recorder recognizes generated glacier ice, but the prediction called the surrounding ice land. Under WM-D29 sparse four-block observations could therefore paint isolated pale rectangles over the otherwise unglaciated chart. The real-data regression recreates those patches and verifies that observations and predictions now agree on ice. This establishes one reproducible cause, not proof that every rectangle in the original screenshot had that origin. Incomplete-column recordings are also rejected now.
* **#22c (Wmap precedence, fixed for either chunk age):** the coordinator reported that the save `andris kingdom story` may predate Earth pre.8 (not confirmed), and the place has existing chunks. `ViewTiles.Display` sorted by level before layer: a newly sampled one-block predicted river drew **over** four-block observed dry terrain. `TileAtlas.Display` also emitted fallback observations before incoming requested predictions, and both `AtlasDialog` and `WmapMinimapLayer` faded non-flat observations along with prediction detail; Earth recordings were omitted entirely beyond detail zoom. Existing recordings need neither new WCL6 metadata nor deletion to get precedence. Unknown cells still use the prediction and a real recorded lake/river remains water.

## WM-D41: play-test #36, zoom detail over recorded ground (0.5.0-pre.13, 31 October 2026)

**Decision:** draw tiles coarse level first, a prediction below a recording of its own level (WM-D29's order). ## WM-D45: the climate raster on Earth's built-in heights (0.5.2, 5 November 2026)

**Task:** the author's new 1:10 Earth world on full Copernicus GLO-90 heights (Earth 1.0.3-tall.7, all 26,475 tiles on the machine) took about 6 minutes to load. Wmap's climate raster was the second-largest part: "Climate raster 1024 x 512 ready in 116.0 s" in the server log, right after the player joined. Earth decision 0051 records the cause and a scratch fix that was never committed; this adopts it.

**Cause.** `AtlasServer.BakeClimate` samples `WorldSource.Biome` at every texel's centre on shared pool threads (`Parallel.For`). `Biome` calls Earth's `ForestPotential`, which with local alpine ecology reads the column's own height through `GetColumn`, and on full GLO-90 that decodes the place's tile. Sampled across the globe, the raster decoded tiles everywhere. Earth recognises the world chart's dedicated threads by name ("Wmap world chart", `FineElevation.SweepThreadNames`), but it can't tell the raster's pool threads from far terrain's workers. Those make the biome tiles near the player and must read GLO-90.

**Decision.** `Integrations/EarthHeights.OnBuiltInHeights` finds Earth's public static `EarthMap.Core.FineElevation.BuiltInOnly` by reflection in the Earth model's assembly. It wraps a sampler so each call saves the thread's value, sets it to true, samples, and puts the old value back in a `finally`. `WorldSource.WorldBiome` is `Biome` wrapped that way, or null when Earth has no such property (Earth before 1.0.3, no Earth). `BakeClimate` uses `WorldBiome ?? Biome` and its log line says "on Earth's built-in heights" when the switch is used. Nothing else changes: biome tiles, semantic tiles and the chart keep their samplers. The climate raster's cache name is unchanged, so a raster already baked from GLO-90 stays until the world's cache is rebuilt for other reasons. Both are pictures of the same climate at about 0.35° per texel.

**Why per sample.** A pool thread runs one row of the raster at a time and nothing else meanwhile, but the next work item on the same thread may be a far-terrain tile. Earth's own contract for shared threads is to set the switch around each sample (0051 Implementation). The thread-static write is negligible beside a `ForestPotential` call. Under the switch Earth's GLO-90 readers return before touching any cache: the summit-lift cache isn't filled and no square is marked as fallen back (Earth `FineElevation.TryHeight`, `TrySmoothHeight`, `TryHighest`; `TerrainModel.FineSummitOf`), so a later GLO-90 sample on that thread is as before.

## WM-D46: detail tiles draw rivers from their own water (0.5.2, 5 November 2026)

**Report.** The author's atlas in chart style over the Niagara in their new 1:10 Earth world (3.7 blocks per pixel, "450 detail tiles", "8 tiles pending"). It showed two dark patches with straight edges. The author guessed "keeping larger scale image".

**Cause, lower Niagara.** The map shader replaced a predicted tile's river with the world chart's channel (`map.frag`: `if (uTileSlot.w < 0.5 && uTileInfo.z > 1.5) t.river = b.river`). It did this for every predicted tile coarser than 1.5 blocks per texel; one-block tiles kept their own water since 0.4.3. The chart is 8,192 × 4,096 texels, 489.3 blocks each at the author's ring of 4,007,936. `BaseRaster.DrawRivers` writes the signed distance to the bank at each texel's centre, square-root encoded. The GPU interpolates the encoded bytes, so:
- A river narrower than a texel draws ink only near texel centres. Ink needs a distance below about half a pixel, so between centres the line breaks unless a texel spans about one pixel or less, and predicted detail is drawn only where it spans two or more.
- Where a texel centre lies in or near a big river, the near-zero band stretches over a good part of a texel. The lower Niagara runs along a column of centres, so its channel became a lens about one texel long: ink 30 to 85 blocks either side of the river, the channel's inside washed.

With 2- and 4-block tiles the lens lay round the tile's own river: a second, darker river. Its straight bottom and left edges in the screenshot were where the player's recorded terrain, which already kept its own water, was drawn over it.

**Other patch, Lake Erie's east shore.** A straight shore with a dark band and straight depth lines is the world chart itself, drawn where no detail tile is yet. The offline render of the chart alone at that place matches; with 2-block tiles the shore is detailed. Eight tiles were pending, and the logs show no tile errors. No change.

**Decision.** Predicted tiles no longer take the chart's river channel at any level. `decode` already leaves a tile's river `Far`, and the shader's only use of `b.river` for tiles is gone. Rivers come from the tile's water, as for one-block and recorded tiles. The chart still draws its river lines where it is drawn alone (beyond detail zoom). While predicted detail fades in (a chart texel 2 to 4 pixels), the chart under the tiles still shows its lines. A river narrower than a tile's texels is not drawn at that zoom; the chart's channel could not draw it there either, apart from blobs near texel centres. Per-tile river distances from the server's river segments would draw such streams, but they need a fifth channel in the tile format. Not done.

**Verification.**
- **Offline renders of the author's view.** A scratch harness built Earth 1.0.3-tall.8's model at the author's geometry (ring 4,007,936, height 1024, sea level 110, GLO-90 river courses; 2,285,344 river segments, as in the server log).   - The lens appears with 2- and 4-block tiles, as in the screenshot.
  - With the new shader the renders change only inside one box round the lens, 77 × 380 pixels of a 3,600-pixel-wide view: about 16,000 pixels in each style. Nothing else in the reported view changes, and renders of the chart alone are identical.
  - The Lake Erie render with 2-block tiles is unchanged.

A 30-block river runs through a column of 512-block chart texel centres, drawn with 2- and 4-block tiles at 3.7 blocks per pixel. The check counts river-blue land pixels more than 25 blocks from the river: 20,499 (chart style) and 27,000 (terrain style) with the 0.5.2 shader before this change, 0 with it; the limit is 50.

## WM-D47: ore heat maps on the Creative map (0.5.2-ore.1, 5 November 2026)

Made on `claude/ore-heatmaps` as 0.5.2-ore.1, then joined with WM-D45 and WM-D46 in the 0.5.2 test build (verification of the joined build in `testing.md`).

**Author direction (5 November 2026, relayed by the coordinating session):** "in Creative we should have options to see heat maps for each ore spawn. Quick check looks at random location feels like little ore. Heat maps would help also debug". Wmap draws the maps because it owns the Creative map. The ore model stays with whichever mod owns the deposit generators (Earth for regional ores), queried only through vanilla's public deposit API. **Proposal, not agreed:** this split of ownership. The number WM-D47 skips WM-D45 (climate test build) and WM-D46 (reserved for parallel river work) and may need renumbering when the branches merge.

**Design.** The server catalogue mirrors the prospecting pick (`ProPickWorkSpace`): every deposit variant with an ore map, children included, the last variant per code winning. One value per grid cell, one ore per request (or every ore for "ores the pick lists"):

- A generator that answers the pick anywhere (`EarthMap.EarthOreGenerator`) is asked for its own `GetPropickReading` at the centre chunk of each cell, with no column and no generated chunk, at the ground height Wmap's prediction or the loaded heightmap gives. Blocks per chunk = ppt / 1000 × surface height × 1024, the pick's own formula turned around. Earth's reading is thread-safe, so a request runs on up to four threads (half of `Threads`).
- A vanilla `DiscDepositGenerator` has no such answer without the chunk's rock column. The map uses the loaded region's ore map factor × the variant's average quantity × the world's deposit rate (`deposits.json`'s chance multiplier, heights over 256 scaled as vanilla scales tries). It is an upper bound: vanilla places ore only in its host rock, which the map does not count. Cells in unloaded regions have no answer, and "ores the pick lists" is not offered, because it would over-count. Other generator types are skipped.

The grid is chosen from the view: the finest power-of-two chunk spacing (32 to 16,384 blocks) that gives each cell at least 10 screen pixels (20 for the listed count), at most 160 × 160 cells, snapped to the spacing with a one-cell margin, so a small pan reuses the map and only a real move asks again. The client asks once the view has been still for 300 ms. Per player, the newest request replaces one still waiting, and a running sample stops when a newer one arrives. At most four finished maps go out per tick, only to players who are still allowed. Colours run blue, green, yellow, red over 1 to 10,000 blocks per chunk on a log scale (0 to 8 ores for the listed count), translucent at depth 56 under the wind layer, labels and menus. The hover line gives the cell's blocks per chunk and the pick's word for its factor (listed above 0.025; word index = factor × 7.5).

Never on the game chart; access is the Creative map's (creative mode, the `wmap` privilege or `AllowAllPlayers`). Protocol: `AtlasInfo` fields 40 and 41 and two appended message types.

## WM-D48: ore heat maps in stored tiles at every zoom (0.5.2, 6 November 2026)

**Author direction (6 November 2026, with a screenshot of bituminous coal over Europe):** "i only renders once selected in given zoom, then it does not update. Idea was to pregenerate images and store them and can see at any zoom". The screenshot showed the map of an earlier, closer view (about 0 to 16 E, 45 to 53 N) after zooming out, with the status line still "working out Bituminous coal over 133 × 68 cells of 2048 blocks".

**Cause.** WM-D47 asked for one grid over the whole view and drew nothing new until the server had sampled every cell of it; the old map stayed up meanwhile. Every zoom past a cell-size step threw the grid away and asked again, a newer request stopped the one in progress, and nothing was kept between views or ores. How long the author's 133 × 68 grid took is not known: the server log has no ore heat failure, and offline (Earth's built-in heights, not the GLO-90 store the author's world may use) a grid that size took about a second.

**Design.**

- **Tiles.** The ore map uses the atlas's own tiles (`TileKey`: level L spans 128 × 2^L blocks from the ring's start, `TileSelection.Visible` picks a view's tiles on every copy of the ring) with 32 × 32 cells, so a cell is 4 × 2^L blocks: one chunk at level 3 (the finest) up to one tile for the whole world. The view takes the finest level whose cells are at least 10 screen pixels. A cell is sampled at the centre of the chunk at its centre, as before; cells past the ring's east end or the south edge have no value (the next copy's first tile covers them).
- **Every ore per tile, stored.** The server works a tile out for every ore at once: one surface height per cell (the loaded chunk's, else the terrain prediction, else sea level; only where some ore answers by reading, since vanilla's ore maps need none), then each ore at that column, on up to four threads (half of `Threads`). A complete tile is stored in the world's cache folder beside the atlas's tiles (`o-<catalogue>-<level>-<x>-<z>.wmt`: deflated half floats, blocks and factor per ore and cell) and counts against the same `DiskCacheMiB` limit, the oldest trimmed first. The catalogue id hashes the ores, their generators (type and assembly), their amounts, the world height, seed and tile size; the folder itself is already per world, mod set and terrain. 48 tiles stay in memory, so switching ores over a view reads nothing. An answer is one ore's two arrays (8 KiB), or the listed count and strongest factor worked out from the stored tile.
- **Stored ahead.** Where every ore answers anywhere (Earth's readings), the first request of a server run starts storing the coarse levels of the whole world: whole levels from the top down while they fit in 1,000 tiles, on two threads of their own at below-normal priority. Tiles already stored are skipped, so this is done once per world. Vanilla's ore maps answer only in loaded regions, so nothing is stored ahead there, and a tile with a missing region is not stored; the client asks for it again after 20 s.
- **Client.** Every frame the view's tiles at its level are drawn if the client has them. A missing tile is drawn from the nearest coarser tile it has (each cell taking the coarser cell it lies in) until it arrives; the hover line says so. Once the view has been still for 150 ms the client asks for the missing tiles, nearest the middle first, each one's tile two levels up first where nothing coarser covers it, at most 64 per request. A newer request replaces the tiles of the older one on the server; the tile in hand is finished and still sent. Players are served in turn, a tile at a time, and at most 16 answers go out per tick. Up to 1,024 tiles (of every ore asked for) are kept on the client, the least recently drawn dropped first.
- Protocol (still unreleased 0.5.2): `OreHeatRequest` is now an ore code with level, x and z arrays; `OreHeatResponse` one tile with a partial flag and the stored-ahead count. Fields 40 and 41 of `AtlasInfo` are unchanged.

**Verification:** see `testing.md`, "0.5.2: ore heat maps in stored tiles".
